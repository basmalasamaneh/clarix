Phase 6 — Runs list and Comparison page. Read docs/CLARIX_SPEC.md (§3 metrics, §8 comparison page, §12 design system) and replit.md first. Build ONLY this phase.

Goal
A user picks two production runs (orders) and sees a clear, checkable comparison of scrap, changeover time and downtime. Code calculates, the browser only displays. Every number must be traceable to its source rows (the Source Drawer comes in Phase 7; here just expose a "Show source" link target/placeholder with the row references already available in the API).

1. Runs list (e.g. /runs)
 - Table (cards on mobile) of current orders from approved, non-archived sources: order id, source name, date, input kg, good kg, scrap kg, scrap rate, changeover minutes, overall StatusBadge.
 - Missing values show "Not available", never 0.
 - Search by order id; filter by status and source. Sort by order id or status.
 - Select two runs to compare; the Compare button is enabled only when exactly two are selected.
 - Orders from different sources with the same order id must be clearly distinguishable by source name.

2. Comparison page (e.g. /compare?a=...&b=...)
 - Two columns (Run A, Run B) and a Difference column.
 - Metrics from the locked spec: input, good, scrap, scrap rate (%), good rate (%), material balance, changeover minutes (sum of end-start of CHANGEOVER events), unplanned downtime minutes (shown SEPARATELY, never merged into changeover, never claimed as a cause).
 - Differences in percentage points for rates (e.g. +5 pp) and in minutes/kg for amounts, with sign. Display rounding ROUND_HALF_UP; calculation with exact decimals.
 - Per-group StatusBadge (Volume / Changeover / Downtime) and an overall status. If either run is red/blocked (e.g. SUSPECTED_DUPLICATE_RECORD), the comparison is NOT shown; show the reason and a link to the Data Quality page instead.
 - If either run has warnings (yellow), show the comparison with a visible warning banner listing the issues and a link to each in Data Quality.
 - Plain-language summary sentence generated by code templates (not AI), e.g. "E-02 had 5 percentage points more scrap than E-01." Facts only; never claim causes. Include the line: "Downtime is recorded separately and is not assumed to explain the difference."
 - Expected baseline check: E-01 5% / 240 min; E-02 10% / 360 min plus 45 min separate unplanned stop; difference +5 pp and +120 min (2 h).

3. API
 - Server computes everything using the existing lib/calculation engine. No metric math in the browser.
 - Responses include for each number its source row references (file, physical line, column).
 - Factory-scoped on the server; Ethmar never sees Najm. Viewer can read.

4. UI/UX
 - Arabic RTL + English LTR, light + dark, green brand, tokens only. 360px / 768px / 1280px. On mobile the comparison stacks into metric cards.
 - Not colour alone for meaning. Keyboard accessible. Loading, empty, error and "not comparable" states designed.
 - NO charts in this phase (charts are Phase 11/wave 2).

5. Tests
 - Load every fixture through the real pipeline and compare ALL displayed metrics and differences to expected/expected_results.json for all 25 Ethmar scenarios plus Najm baseline. Report a table scenario | metric | expected | actual | PASS/FAIL.
 - Specific: missing values render "Not available" (never 0); blocked runs are not compared; same order id from two sources are distinguishable; yellow runs show the banner; decimal exactness (no float).
 - Tenancy tests for runs and comparison (T1, T2, T3, T4).
 - Tests run in an isolated target and must not write to Ethmar/Najm dev factories; show before/after counts.
 - Screenshots: runs list and comparison, 360/1280px, Arabic/English, light/dark. State clearly you cannot judge visual quality.

Do NOT build: Source Drawer, charts, PDF/export, AI, snapshots, reconciliation, resolve workflow.

Final report: built / not built, scenario metric table, test results, before/after counts, and exact manual steps for me.
